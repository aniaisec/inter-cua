# Benchmark

This benchmark asks one question: is discovering a workflow once and replaying
it deterministically better than asking a model to operate the UI every time?

It compares three strategies on the same tasks, against the same mock app,
under the same policy, credentials and injected failures:

| Strategy | What runs | Model calls |
|---|---|---|
| `baseline_llm` | The discovery loop used as an agent, fresh on every invocation: goal → observe → decide → act, until done or stuck | every step |
| `inter_cua_discovery` | The one model run that turns the goal into a capability (recorded as a draft beside the run, never approved here) | once per capability |
| `inter_cua_replay` | The approved capability through `cua.replay.runner.replay`, exactly as `cua replay` runs it | none |

The baseline gets the same prompt, tools, policy checks and screenshots that
produced the committed capabilities. It also gets a fresh browser per
invocation, as replay does. When a task gives consent for the risky step,
replay receives a signed approval token and the baseline has its risky
actions approved. Each strategy gets the same consent, in its own form.

## Layout

```
bench/
  tasks/core.yaml     the suite: 15 unattended tasks and 1 that needs a person
  scripts/            tool-call scripts for --llm scripted (no key)
  pricing.yaml        model prices, with source and date, for cost estimates
  reports/runs.jsonl  one line per invocation (raw, append-only)
  reports/sessions.jsonl   one line per session: versions, commit, model
  reports/summary.{json,md} generated by `cua benchmark report`
  runs/               run directories (logs, screenshots); gitignored
```

## Running it

```bash
cua benchmark list                          # the tasks and their ground truth
cua benchmark run                           # all tasks, all strategies, scripted model (no key, no cost)
cua benchmark run --llm gemini --task lookup-success --repetitions 3   # a live model: costs money
cua benchmark run --strategy inter_cua_replay --repetitions 50         # replay only, no model
cua benchmark report --latest               # summary of the last session
```

Each session starts its own mock app on a free port, so its commit counter
starts at zero and a running `cua mockapp` is left alone.

`--llm scripted` is the default. It plays a recorded tool-call sequence in
place of a model, so the whole harness runs offline. Its model calls, tokens
and cost are zero by construction, and its success rate measures the harness,
not a model. The report says so at the top. Compare strategies only on a
live-model session.

## Scoring

Each task states its ground truth: what a correct operator would conclude,
written independently of either strategy.

- `answer`: the task has one (outputs; decimals compare numerically, `re:`
  values are regular expressions).
- `business_outcome`: the app's answer is a declared business fact
  (`NOT_FOUND`, `PERMISSION_DENIED`, `VALIDATION_ERROR`).
- `refusal`: the right thing is to deliver nothing and change nothing.
- `commits`: how many irreversible commits a correct invocation makes.

Every invocation is scored as one of:

| Match | Meaning |
|---|---|
| `exact` | the correct answer, with the right side effects |
| `safe_stop` | no answer and nothing wrong done: failed or escalated cleanly, for a person to pick up |
| `wrong` | a wrong answer, or a commit that should not have happened (without consent, or a second time for the same request) |

Side effects are scored on the app's own record, not the strategy's claim.
The mock app's `/_debug/stats` counts commits across every session, and the
harness reads that count before and after each run.

The baseline has no typed channel for a business outcome. When it stops, a
stated reason that matches the task's declared `baseline_pattern` counts as
the right answer. This judge is a heuristic, declared per task so it can be
read and argued with.

## Metrics

Each row in `runs.jsonl` records:

- **Outcome:** the match, what the strategy returned, and the ground truth.
- **Timing:** wall clock and time spent waiting on the model.
- **Model usage:** model calls, and input, output, thinking and cache tokens.
- **Model identity:** provider and the model version that answered.
- **Cost:** the estimated cost.
- **Run behaviour:** actions, recoveries, locator slips, policy blocks,
  escalation, and human intervention.
- **Side effects:** the side effect as reported, commits the app observed,
  and duplicate or unexpected side effects.

`cua benchmark report` recomputes everything from those rows. It reports
success, safe-stop and wrong rates (success with a Wilson 95% interval), and
latency (mean, median, nearest-rank p95, standard deviation). It also gives
model calls and tokens per run, cost per run and per success, success after
1/10/50/100 repetitions, and a per-tag view (drift, recovery, side effects).
When all three strategies are priced, it adds a model-cost break-even:
discovery ÷ (baseline per run − replay per run).

When the run directories are still on disk (`bench/runs/`, not committed), the
report adds *where the time goes*: each strategy's mean seconds per run in model
waits, acting, locating, settle-and-verify, per-step evidence and startup,
adding up to the wall clock. `cua metrics run <run_id>` explains one run.

Costs are estimates from `pricing.yaml`, not billing data. A model with no
entry is reported as unpriced, never as free.
